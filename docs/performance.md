# מדידת ביצועים

## איך נמדד

- **נתונים:** 100,000 פניות (`--seed --reset`). הטבלה כולה: **2,035 דפים** (דף = 8KB).
- **השאילתות:** ה‑SQL המדויק ש‑EF Core שולח, מתוך הלוג של השרת.
- **המדדים:** Actual Execution Plan, ו‑`STATISTICS IO/TIME`. **Logical reads** = כמה דפים המסד קרא. ככל שהמספר קטן יותר, השאילתה טובה יותר.

## התוצאות

| פעולה | Execution Plan | דפים | זמן |
|---|---|---|---|
| **רשימה רגילה** (עמוד 1) | Index Scan על `CreatedAt`, עוצר אחרי 20 | **71** | 0ms |
| **ארגון + סטטוס + עדיפות** | Index Seek על אינדקס הארגון | **81** | 1ms |
| סיכומים לפי סטטוס | Index Scan + ספירה | 729 | 35ms |
| חיפוש מילה נפוצה (עמוד) | Index Scan, עוצר אחרי 177 שורות | 554 | 3ms |
| **חיפוש מילה נדירה** (עמוד) | עובר על כל 100,000 השורות | **306,892** ❌ | 837ms |
| `COUNT` של חיפוש | סריקה של כל הטבלה | 2,035 | ~470ms |

### פעולה 1: רשימה רגילה
```
Top (20)
 └─ Index Scan   IX_Requests_CreatedAt   (ממוין כבר, נקראות רק 20 שורות)
     └─ Key Lookup ×20                    (שאר העמודות)
```
האינדקס כבר ממוין לפי תאריך, ולכן אין מיון ואין סריקה של הטבלה. **בלי האינדקס:** כל הטבלה (2,035 דפים) ומיון של 100,000 שורות.

### פעולה 2: ארגון + סטטוס + עדיפות
```
Top (20)
 └─ Index Seek   IX_Requests_OrganizationName_CreatedAt
       Seek:  OrganizationName = 'Globex'          (קפיצה ישירה לארגון)
       Where: Status, Priority                     (נבדקים בתוך האינדקס, בזכות INCLUDE)
     └─ Key Lookup ×20
```

## האינדקסים ולמה

| אינדקס | התרחיש |
|---|---|
| `(CreatedAt)` | מסך הפתיחה, טווח תאריכים |
| `(Status, CreatedAt)` | סינון וסיכומים לפי סטטוס |
| `(OrganizationName, CreatedAt)` INCLUDE `(Status, Priority)` | פניות של ארגון |
| `(AssignedTo, CreatedAt)` INCLUDE `(Status, Priority)` | פניות של מטפל |
| `(RequestId, ChangedAt)` בהיסטוריה | ההיסטוריה של פנייה |

**העיקרון:** עמודת הסינון ראשונה, ו‑`CreatedAt` (המיון) בסוף. המסד קופץ לשורות ומקבל אותן כבר ממוינות.

**לפני ואחרי** (דפים / זמן. נמדד כשהאינדקסים נוספו, על גרסה מוקדמת יותר של המסד, ולכן המספרים שונים מעט מהטבלה למעלה):

| תרחיש | בלי אינדקסים | אינדקסים | + INCLUDE |
|---|---|---|---|
| רשימה רגילה | 2,035 / 144ms | 211 / 4ms | 215 / 3ms |
| status=New | 2,035 / 31ms | 153 / 3ms | 145 / 2ms |
| **ארגון + סטטוס + עדיפות** | 2,035 / 25ms | **5,029** / 35ms ❌ | **176** / 5ms ✅ |
| סיכומים לפי ארגון | 2,035 / 47ms | 310 / 34ms | 44 / 4ms |

**הלקח:** אינדקס על הארגון לבד **החמיר** את הסינון המשולב, כי כל שורה של הארגון דרשה גישה לטבלה כדי לבדוק סטטוס ועדיפות. INCLUDE פתר את זה.

**לא קיבלו אינדקס:** Priority לבד (רק 3 ערכים), ומיון לפי שאר השדות (פחות נפוץ, וכל אינדקס מאט כתיבה).

## אין טעינה מלאה לזיכרון

השאילתה נבנית כ‑`IQueryable` ונשלחת כ‑SQL אחד, עם `WHERE`, `ORDER BY` ו‑`OFFSET/FETCH`. לשרת מגיעות רק שורות העמוד. גם `totalCount` והסיכומים מחושבים במסד. **בתוכניות:** הפעולה העליונה היא `Top (20)`, ונקראות רק 20 שורות מהטבלה.

## Bottleneck: החיפוש החופשי

**הבעיה:** `search` מתורגם ל‑`LIKE '%term%'`. כשהתבנית מתחילה ב‑`%` אין אפשרות להשתמש באינדקס, וכל שורה נבדקת. לכן ה‑`COUNT` של כל חיפוש סורק את כל הטבלה.

**המקרה הגרוע:** בעמוד של חיפוש, המסד מניח שימצא 20 תוצאות מהר ועובר לפי תאריך. במילה נפוצה זה מצוין (3ms). במילה נדירה הוא עובר על כל 100,000 השורות (837ms). ניסיון לבטל את ההנחה הזו (Hint) שיפר את המילה הנדירה (455ms), אבל האט את הנפוצה (455ms), ולכן לא אומץ.

**הצעת שיפור: Full‑Text Search** של SQL Server. אינדקס הפוך (לכל מילה, השורות שמכילות אותה) הופך את החיפוש ל‑Seek. השינוי: `CREATE FULLTEXT INDEX` ב‑Migration, ו‑`EF.Functions.Contains` במקום `Contains`. לא מומש כי LocalDB לא תומך בו.
